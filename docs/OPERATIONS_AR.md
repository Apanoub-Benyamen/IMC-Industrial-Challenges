# التشغيل الفني

## المتطلبات والبنية

Node.js 24 LTS، بدون حزم npm خارجية. خادم HTTP مدمج، SQLite مدمجة، واجهة HTML/CSS/JavaScript، وخط عربي محلي. لا تعتمد الواجهة على CDN أو اتصال إنترنت أثناء العرض بعد تثبيت Node.

إعدادات `.env.example` تنسخ إلى `.env` عند الحاجة ويستخدم `node --env-file=.env server.mjs`. `npm start` لا يحمل الملف تلقائيا. `DATA_DIR` مسار قاعدة البيانات والمرفقات؛ `PORT` الافتراضي 3000؛ `HOST` الافتراضي 0.0.0.0 لأغراض المعاينة. محليا يمكن تقييده إلى 127.0.0.1. لا تنشر المنفذ مباشرة.

## تجهيز تشغيل فعلي

1. مجلد بيانات جديد تماما، دون seed ودون أي حساب تجريبي. يمنع الخادم تشغيل قاعدة تحتوي حسابات imc-demo.test في الوضع الإنتاجي.
2. `DEMO_MODE=false` و`APP_ORIGIN=https://...` مطابق تماما لأصل الموقع بلا شرطة نهاية.
3. HTTPS عبر reverse proxy موثوق، وتمرير Host الأصلي، وحد طلب 6 MB، timeouts، ومحددات معدل وقياس أداء.
4. ربط البريد وفحص الملفات كما يلي. يجب أن تكون الخدمات HTTPS خاصة وموثوقة ولا تسجل المحتوى الحساس في سجلات عامة.
5. إنشاء مسؤول عبر `node --env-file=.env admin.mjs`؛ كلمة المرور تكتب في الطرفية بإخفاء الأحرف. لا توجد كلمة مرور إنتاجية افتراضية. يملك مشغل الخادم صلاحية إنشاء المسؤول، فاحم وصوله.
6. مراجعة أمنية مستقلة، MFA للإدارة، اعتماد سياسات المركز، اختبار إرسال البريد وملفات سليمة ومرفوضة، واستعادة النسخ الاحتياطية.
7. شغل كخدمة تحت مستخدم نظام محدود مع إعادة تشغيل ومراقبة. لا تشغل بصلاحيات root. راقب المساحة والأخطاء وقيود المعدل.

## عقد البريد

POST إلى `MAIL_WEBHOOK`، Content-Type application/json، Authorization: Bearer من `MAIL_WEBHOOK_KEY`.

```json
{"to":"recipient@example.com","subject":"تأكيد البريد الإلكتروني","url":"https://approved-origin/#verify/one-time-token"}
```

ترسل الخدمة رسالة للمستلم وتتجاوب بكود 2xx عند قبولها؛ مهلة الخادم 10 ثوان. الفشل يعاد كخطأ ويمكن إعادة الإرسال من الإعدادات. لا يخزن الخادم بريد الإنتاج في صندوق العرض. الروابط توكنات حساسة؛ لا تسجلها في التحليلات.

## عقد فحص الملفات

POST إلى `SCAN_WEBHOOK` مع جسم binary وContent-Type application/octet-stream وAuthorization Bearer من `SCAN_WEBHOOK_KEY`. النتيجة المقبولة فقط 2xx وJSON:

```json
{"clean":true}
```

المهلة 15 ثانية. أي نتيجة أخرى تمنع حفظ الملف. ينفذ مزود الخدمة مكافحة البرمجيات الضارة والتحقق من صيغة الملف. واجهة التكامل جاهزة؛ مزود البريد ومحرك الفحص غير مرفقين بهذه الحزمة.

## النسخ الاحتياطي

للنسخة المحلية: أوقف الخادم ثم انسخ مجلد DATA_DIR كاملا، شامل imc.sqlite وأي ملفات WAL/SHM باقية ومجلد uploads. استعده إلى نفس DATA_DIR عند توقف الخادم ثم ابدأ التشغيل. لا تنسخ قاعدة مفتوحة وحدها بطريقة عادية. في التشغيل الفعلي استخدم SQLite backup API أو snapshot متسق وخطة احتفاظ مشفرة، واختبر الاستعادة.

لا يوجد زر حذف شامل أو reset تلقائي متعمدا. لإنشاء تجربة منفصلة استخدم DATA_DIR جديدا بدل حذف بيانات موجودة. seed.mjs لا يضيف حسابات إذا كانت قاعدة البيانات تحتوي مستخدما.

## هيكل API

`/api/session`, `/api/login`, `/api/register`, `/api/verify`, `/api/forgot`, `/api/reset`, `/api/logout`, `/api/password`.
`/api/profile`, `/api/factories`, `/api/factories/:id`, `/api/registration/submit`, `/api/upload`, `/api/files/:id`.
`/api/cases`, `/api/cases/:id`, `/api/cases/:id/comment`, `/api/cases/:id/review`.
`/api/admin/registrations`, `/api/admin/registrations/:id`, `/api/admin/export`, `/api/admin/audit`, `/api/notices`.
`/api/mail` متاح لحساب المستخدم في وضع العرض فقط.

كل التعديلات POST، وكل القراءة GET. الـCSRF يعود من session/login ويرسل في X-CSRF-Token. لا تحفظ الجلسة في localStorage. بيانات النماذج تخزن JSON في cases.form مع أعمدة أساسية للبحث والحالة؛ التوسع إلى reporting schema منفصل مستقبلي.

## تحديث 2

تضاف جدول partners تلقائيا عند التشغيل باستخدام CREATE TABLE IF NOT EXISTS، دون حذف أو إعادة تهيئة أي بيانات قائمة. إضافة partner/program/sector ومتابعة التنفيذ داخل assessment بصيغة JSON، فلا تحتاج migration يدويا للأعمدة.

النقاط الجديدة: POST /api/register-complete (multipart، ملف payload بصيغة JSON ومستندات commercial/tax/authorization وindustrial_0 وما بعده)، GET/POST /api/admin/partners، GET /api/admin/registrations-export (XLSX).

يسمح ملف التسجيل حتى 20 مصنعا مع حد طلب 120 MB وكل مستند حتى 5 MB. اضبط حد reverse proxy لمسار التسجيل على 120 MB، مع الإبقاء على 6 MB لمسار رفع مرفق منفرد. في بيئة المؤسسات يفضل تحويل التسجيل إلى رفع مباشر لمخزن خاص ومعالجة مهام بدل تخزين جسم الطلب في الذاكرة. لا ينشئ تسجيل كامل أي صفوف حسابات أو ملفات عند فشل التحقق.

الإسناد في هذا التحديث سجل إداري وليس مشاركة وصول أو إرسالا تلقائيا للجهة. لا تنشئ الجهات قبل إدخال بياناتها المعتمدة من المركز؛ يبدأ الدليل فارغا.

## تحديث 3

تركيب الملفات كما في `UPDATE_V3_AR.md` عند توقف الخادم، مع الاحتفاظ بمجلد البيانات والاعدادات. ينشئ بدء التشغيل الجداول الاضافية `support_tickets`, `support_messages`, `info_requests`, `info_answers`, `project_updates` باستخدام IF NOT EXISTS. لا توجد خطوة اعادة seed.

واجهات جديدة: `/api/cases/:id/answer` و`/api/support` و`/api/support/:id` و`/api/actions` بفلاتر from/to/action و`/api/tasks`. جميعها تتطلب الجلسة والصلاحيات؛ الطلبات المعدلة تتطلب CSRF. سجل التدقيق الفني يبقى في الخلفية ولا تعرضه واجهة الادارة.

تغيير اللغة يستخدم قاموسا محليا ولا يرسل بيانات المستخدم لخدمة ترجمة. اخطار البريد وفحص الملفات تبقى حسب الاعدادات السابقة. التحديثات الدورية للجامعة تتطلب بوابتها وصلاحياتها وتكاملها في مرحلة لاحقة؛ تسجيل التقدم الحالي توثيق من موظف المركز.
